The verdict

This has never executed a single line of its own kernel.

Not "boots but needs a keyboard driver." The BIOS loads sector 1, jumps to 0x7C00, and the first bytes it runs are the GDT descriptor interpreted as machine code. It never reaches _start.

That's baked into the committed floppy.img, so every timing claim and "functional operating system" line in the old README describes something that never happened.

Two ways to see it, straight out of the committed binaries:

bin/boot.bin [0..7] 18 00 06 7C 00 00 00 00 └──┴──┴───── dw gdt_end-gdt_start = 0x0018 (24) └─ dd gdt_start = 0x00007C06 bin/kernel.bin[0..7] CF FA ED FE 0C 00 00 01 └──┴──┴──┴── MH_MAGIC_64 (Mach-O, little endian) └──┴──┴──┴─ cputype 0x0100000C = ARM64

The first is the section ordering. boot.asm had four %include directives above its own section .text, and with -f bin everything they emit lands in .text first — so the GDT descriptor sits at offset 0 and _start is buried a few hundred bytes in. The signature at 0x1FE is still 55 AA, so the BIOS boots it into garbage perfectly happily.

The second one is funnier. The file being dd'd in as the kernel is an Apple Silicon Mach-O object — host gcc on the Mac, then copied rather than linked by cp build/kernel.o bin/kernel.bin. Which means link.ld had never run once, and it pointed at . = 1M while the bootloader loads to 0x1000 anyway.

Honestly this is good news. I'd been extending something I assumed was a working base, and it wasn't. So: make one thing true and verifiable first, then don't let it go untrue again.

Where the guide is wrong

The week-by-week guide I've been following is a decent skeleton and it's right more often than not. But there are a few places where following it literally costs weeks, and those are worth writing down before I start.

It has me build the interrupt layer twice

It does a 32-bit IDT in week 4, then a 32-bit PIC, timer, keyboard and shell in weeks 5–7, then long mode in week 11 — and then casually says to "rebuild the GDT and IDT with proper 64-bit descriptors" in week 12. That's not a tweak. Gate descriptors go 8 → 16 bytes, pusha doesn't exist in 64-bit mode, the frame layout changes, every stub gets rewritten. Go to long mode before writing a single stub and it only happens once.

It treats a working bootloader as the fallback

Weeks 9–11 are hand-writing a two-stage real-mode loader, which is the worst debugging environment in the whole project — no GDB, no output — and Limine only shows up afterwards as an escape hatch. Backwards. Boot with Limine from day one, get long mode and a memory map and a framebuffer for free, and write my own loader later as its own project, when there's a working kernel to compare against.

It barely mentions IST stacks

Kernel stack overflow → page fault; handling that fault on the same dead stack → double fault; handling that on the same stack → triple fault and a silent reset. That's exactly what the Interrupt Stack Table is for, and #DF, NMI and #MC each want their own. The guide mentions IST once, in passing, in week 12.

Four subsystems are just missing

No signals, no TTY or line discipline, no demand paging or mmap, no page cache. Without the first two Ctrl-C doesn't work and neither does job control, so the "userspace shell" in week 47 isn't really a shell. Without the third every fork copies eagerly and there's no file-backed mapping. Without the fourth every read() hits the disk.

Its panic handler can't say where it is

It dumps registers and stack words — bare addresses, no names. If I build a symbol table and a frame-pointer unwinder in the same week as panic(), then every fault after that prints a real backtrace instead of eight hex values I have to resolve by hand.

The environment advice is for a Mac

"On a Mac that's brew install…" — I'm on Windows with nothing installed. That's not a footnote, it's the blocking first step. And the ARM64 Mach-O sitting in the disk image is exactly what happens when the toolchain question gets handled casually.

Decisions to make once

Four choices that are cheap now and expensive in six months. Make them deliberately, write down why, and stop revisiting them.

64-bit long mode, from the first boot

Not 32-bit protected mode with a migration later. The migration is the single biggest source of rework in the guide, and every modern reference I read assumes x86-64 anyway.

Limine first, your own bootloader as a later exercise

Limine hands you long mode, a higher-half mapping, an ACPI pointer, a memory map and a framebuffer. Keeping your own loader on the critical path means a bootloader bug can block kernel work indefinitely — which is precisely the state this repository is in.

Monolithic, with driver interfaces kept honest

A microkernel is a fine research project and a bad first kernel; you will spend the year on IPC performance instead of on operating systems. Stay monolithic, but define real vtable-shaped interfaces at the block-device and filesystem layers so the abstraction is tested by having two implementations.

Serial is the primary output device

VGA text is for demos. Everything you assert in CI, every panic, every trace goes out COM1 where the host can read it. A kernel whose only output channel is inside the VM is a kernel you cannot test.

The plan

Phases, not weeks. The guide's week numbers implied a precision they never had. The order is real, though: each phase depends on the one before it, and the numbering encodes that dependency chain rather than a calendar. Every phase ends with a check you can run, because "it seems to work" is what produced a disk image containing an ARM64 object file.

00

A toolchain that cannot lie to you

Nothing is installed on this machine. Fix that first, and fix it in a way that makes the Mach-O incident impossible to repeat.

Install WSL2 with Ubuntu and do all kernel work inside it — you get a real POSIX environment, and make, dd and the ELF toolchain behave as every OS-dev reference assumes. Inside WSL, build or install an x86_64-elf cross toolchain plus nasm, qemu-system-x86_64 and xorriso. Then put the whole thing in a Dockerfile so CI and your laptop compile with identical binaries.

Add a hard guard to the Makefile: if $(CC) does not begin with a target triple, abort with an error. The rule is that the host compiler must never be reachable from a kernel build rule.

The trap

Do not skip the cross compiler because "gcc works." Your host compiler targets your host, and the only reason that failure was survivable here is that the resulting bytes never executed. On a kernel that does boot, host-targeted code fails as inexplicable corruption.

Done when x86_64-elf-gcc --version and qemu-system-x86_64 --version both answer inside WSL, and a deliberately-wrong make CC=gcc fails loudly rather than producing output.
01

One thing that is actually true

The goal is a 64-bit kernel that boots in QEMU and prints one line over serial. Nothing else. This is the first time this project will have run its own code.

Write a Limine-booted kernel entry point, a linker script placing it in the higher half at 0xFFFFFFFF80000000, and a COM1 driver. Serial is about forty lines: port 0x3F8, set the DLAB bit in the line control register at 0x3FB, divisor 3 for 38400 baud, FIFO control 0xC7 at 0x3FA, then poll bit 5 of 0x3FD before each byte.

Compiler flags are not optional and getting them wrong costs weeks later: -ffreestanding -mcmodel=kernel -mno-red-zone -mno-mmx -mno-sse -mno-sse2. The red zone is the one that will hurt — the SysV AMD64 ABI lets leaf functions use 128 bytes below RSP without adjusting it, and your interrupt handlers will scribble on exactly that region. It does not fail immediately. It fails weeks later as random corruption under interrupt load, and it is the nastiest bug in this entire document to track down.

Done when make clean && make && make run on a fresh clone prints a line to your terminal via -serial stdio. Not the committed image — a freshly built one.
02

Debug infrastructure, before features

Every hour here buys back ten later. Build all of it now, while the kernel is small enough that you can trust it.

  • kprintf over serial, with %p, %x and zero-padding.
  • panic(fmt, ...): message, every register, CR2/CR3, then cli; hlt in a loop. Plus a KASSERT macro that calls it.
  • A symbol table and a stack unwinder. Emit a sorted name/address table into the image at build time, walk saved RBP frames, and print function+0x1c instead of a bare address. Build with -fno-omit-frame-pointer so the walk works.
  • GDB: qemu-system-x86_64 -s -S opens a stub on 1234. Keep the ELF with symbols alongside the flat image. Learn hbreak — hardware breakpoints are the only kind that work before paging is configured.
  • -d int,cpu_reset,guest_errors for the resets you cannot otherwise explain.
  • An in-kernel test harness plus isa-debug-exit: -device isa-debug-exit,iobase=0xf4,iosize=0x04, then a byte written to port 0xf4 exits QEMU with status (value << 1) | 1. Wrap it as test_pass() / test_fail().
  • GitHub Actions running that harness in the Phase 00 container, so CI fails on a broken kernel and not merely a broken build.
Done when a deliberate null dereference prints a named backtrace over serial, and a deliberately failing test turns the CI run red.
03

Hygiene, and a README that is true

Do this while the repository is still small. Delete bin/, build/, floppy.img and the stray zero-byte Merge file from git and add them to the currently-empty .gitignore. Delete CMakeLists.txt — all 235 lines of it call find_package(Threads) for a freestanding kernel and have never built anything. Delete load_kernel.asm and println.asm, which no file includes.

Cut CREDITS.md down to what you actually used. Citing Understanding the Linux Kernel for a function that fills 2,000 words of video memory is the kind of thing that makes a reader stop trusting everything else in the file.

Rewrite the README to describe only what runs. Two paragraphs, a recorded boot, a table of what works and what is next, and build instructions someone can follow. Drop "v2.0" and "Educational Operating System" — it is version 0.1 of a kernel, and the gap between those two claims is the entire reason this rebuild is happening. Delete the fake command prompt from kernel.c at the same time; it comes back for real in Phase 06.

Done when a fresh clone contains no build artefacts, and every capability claimed in the README can be demonstrated by a command in the README.
04

Interrupts — written once, in 64-bit

Right now any fault triple-faults and QEMU silently resets, which looks exactly like a hang. This phase is what makes the kernel able to report its own failures.

Build a 256-entry IDT with 16-byte gate descriptors. Write stubs for vectors 0–31. The irritating part: vectors 8, 10, 11, 12, 13, 14, 17 and 21 push an error code and the rest do not, so the rest need a stub that pushes a dummy zero — otherwise your frame layout is inconsistent and every register you read is off by eight bytes.

There is no pusha in long mode; push the fifteen general-purpose registers explicitly. Keep RSP 16-byte aligned at the C handler call or any future SSE code will fault on aligned loads. Have the handler decode the exception name, the error code bit by bit, and CR2 for page faults.

Set up a TSS with IST entries now, and point #DF, NMI and #MC at their own stacks. This is cheap today and it is what stops a kernel stack overflow from becoming an unexplainable reset.

Done when a null dereference, a divide by zero and an invalid opcode each produce three different clean dumps with backtraces, instead of three identical silent reboots — and a deliberate infinite recursion prints a double fault rather than resetting.
05

Interrupt controllers and a clock

Remap the 8259 PIC first — it powers up mapping IRQ0 onto vector 8, which is also the double fault vector, so a timer tick is indistinguishable from a catastrophic CPU error. ICW1 0x11 to 0x20/0xA0, offsets 0x20/0x28, ICW3 0x04/0x02 for the cascade, ICW4 0x01 for 8086 mode.

Then mask it off entirely and move to the APIC. Parse the ACPI RSDP that Limine hands you, walk the MADT for the LAPIC and IOAPIC addresses, and route IRQs through the IOAPIC with the interrupt source overrides applied. The legacy PIC cannot do SMP, so if you intend to get there, every week spent building on it is a week you will unwind.

Get a tick from the LAPIC timer, calibrated against the PIT. Keep a global counter, write sleep_ms(), and delete delay_milliseconds() with its for (i = 0; i < ms * 10000; i++) nop loop — it produces a different delay on every machine and every optimisation level.

The trap

Two EOI bugs eat afternoons. On the PIC, an IRQ from the slave (8–15) needs EOI sent to both controllers; forget the slave and that IRQ fires exactly once, forever. And the PIC raises spurious interrupts on lines 7 and 15 — check the ISR register and return without EOI when it is spurious.

Done when get_system_uptime() returns a real monotonically increasing value, and a test asserts the counter advances across a known wall-clock interval.
06

Keyboard, and a shell that is no longer a lie

PS/2 controller: status port 0x64, data port 0x60, IRQ1. Read the scancode, translate it through a set-1 table, handle the 0xE0 prefix for extended keys, track shift/caps/ctrl as state, and push characters into a ring buffer that a blocking getchar() drains.

The discipline that matters: the interrupt handler reads a byte, pushes it, sends EOI, returns. It does not block, it does not allocate, and it does not take a lock that any non-interrupt code holds. All parsing happens in the consumer. Establish this now, because once there is a scheduler, an IRQ handler touching a held lock deadlocks the machine in a way that is genuinely hard to reason about. Dropping keystrokes when the buffer is full is fine; corrupting the buffer is not.

Then the shell: a read-eval-print loop over the keyboard buffer, backspace editing, and a command table mapping strings to function pointers. Implement help, clear, uptime, mem (which prints nothing useful yet — that is fine), reboot via the keyboard controller pulse, panic to demonstrate the fault handler on demand, and echo.

Done when the four commands the kernel has been advertising since 2025 actually run. Record it — this is the first genuinely demonstrable milestone.
07

Physical memory

Take Limine's memory map and build a bitmap allocator over it: one bit per 4 KB frame, pmm_alloc_frame() returning a physical address and pmm_free_frame() giving it back. Mark as reserved everything below 1 MB, the kernel's own extent (take the bounds from linker symbols), the bitmap itself, and every region not marked usable.

Add a free-frame counter so mem prints real numbers. A buddy allocator is better and you do not need it yet.

Done when a test allocates every frame, asserts none repeat, frees them all, and asserts the count returns exactly to baseline. That last assertion catches an entire category of bug for the rest of the project.
08

Virtual memory

Limine already put me in the higher half, which deletes the guide's most painful week. What remains is owning the tables yourself: a four-level walk through PML4, PDPT, PD and PT, with vmm_map(pml4, virt, phys, flags) allocating intermediate tables on demand, plus vmm_unmap and vmm_get_physical. Flush single entries with invlpg rather than reloading CR3, which flushes everything.

Build your own PML4, switch to it, and drop the bootloader's identity mapping once you have jumped. Kernel mappings live in the upper half of every address space and are shared; user mappings live in the lower half and are per-process.

Then make the page fault handler genuinely good, because you will read its output several hundred times. CR2 holds the faulting address; the error code tells the story — bit 0 means the page was present so it is a protection violation rather than a missing mapping, bit 1 means write, bit 2 means user mode, bit 4 means instruction fetch. Decode every bit into English.

Done when you can map a page, write to it, unmap it, and see a correctly-decoded fault — and a thousand map/unmap cycles leak zero frames.
09

Kernel heap

kmalloc and kfree over a free list with block headers, first-fit, coalescing adjacent free blocks. Put magic-number canaries before and after every allocation and check them on free: a heap corruption you catch immediately costs an hour, and one you catch three weeks later costs a weekend.

Track total allocated bytes and live allocation count so tests can assert a subsystem does not leak. Slab caches for fixed-size objects come later, when you have thread structs to allocate.

Done when an adversarial allocate/free/fragment test passes, coalescing is verified by asserting a large allocation succeeds after freeing neighbours, and a deliberate overflow trips a canary.
10

Demand paging and address spaces

Missing from the guide entirely, and everything after it is shaped by whether I have it. Introduce a region abstraction — a VMA describing a range, its permissions, and its backing — and make the page fault handler consult it: a fault inside a mapped region allocates and maps a frame on the spot; a fault outside one is a real fault.

This buys anonymous memory that costs nothing until touched, a growable heap and stack for future processes, file-backed mappings once there is a filesystem, and — critically — it is the mechanism copy-on-write will be built on in Phase 13. Retrofitting it after fork exists means rewriting fork.

Done when a 16 MB anonymous region can be reserved while free frame count barely moves, and frames appear only as pages are touched.
11

Threads, scheduling, synchronisation

The TSS you built in Phase 04 already carries RSP0, the kernel stack the CPU switches to on a privilege transition. Now write the context switch: save the callee-saved registers (rbx, rbp, r12–r15) on the outgoing stack, save RSP into the outgoing thread, load RSP from the incoming one, swap CR3 if the address space differs, pop, ret. That ret returns into whatever the incoming thread was doing, which is a genuinely strange thing to watch work in GDB the first time.

Give every thread its own kernel stack — sharing one is an instant and confusing crash. Get a cooperative scheduler working first, with explicit yield(), because debugging a cooperative scheduler is possible and debugging a broken preemptive one is much less so. Then move schedule() into the timer interrupt, round robin, 10 ms quantum.

Preemption introduces a class of bug you have not met: anything touching the run queue must run with interrupts disabled, or a tick mid-list-manipulation corrupts it. Write irq_save()/irq_restore() and be rigorous. Then spinlocks via lock cmpxchg, and mutexes and semaphores that actually block — the thread leaves the run queue for a wait queue rather than spinning.

The trap

Make the idle thread hlt rather than spin, or QEMU pins a host core at 100% and you will spend a day looking for a performance bug in your scheduler that is really a busy-wait in your idle loop.

Done when N threads incrementing a shared counter M times each under a lock produce exactly N×M in CI. Run it once without the lock and watch it come out wrong — that is the whole reason the lock exists.
12

Ring 3

The hardest conceptual jump in the project. Give it concentrated time rather than three-hour evening chunks.

Add GDT entries for user code and data at DPL 3, then configure the syscall/sysret MSRs: STAR (0xC0000081) for the segment selectors, LSTAR (0xC0000082) for the entry point, SFMASK (0xC0000084) for flags cleared on entry — clear IF, you do not want interrupts enabled before you have switched stacks. Set bit 0 of EFER. Do not use int 0x80; it is the 1990s answer and anyone reading your code will notice.

The entry path is fiddly. syscall does not switch stacks, so on entry you are still on the user stack with user data in every register. swapgs exchanges GS_BASE with KERNEL_GS_BASE (0xC0000102), giving you per-CPU data from which to fetch the kernel stack. Switch stacks, save the user frame, enable interrupts, dispatch; on the way out disable interrupts, restore, swapgs again, sysretq. Note that syscall clobbers RCX and R11, which is why the argument register for the fourth parameter is R10 and not RCX.

The trap

Getting the swapgs pairing wrong on the return path is a privilege escalation in your own kernel. An NMI or #DB arriving in the window where GS is the wrong one is the classic hazard — this is what IST stacks and careful entry sequencing exist for. When you get it right, write it up; that writeup is worth a great deal in an interview.

Done when a hand-written assembly program entered via iretq calls write and exit, and you watch the timer preempt it mid-execution and resume it.
13

Processes, fork, copy-on-write, exec

A syscall dispatch table indexed by RAX, with arguments in RDI, RSI, RDX, R10, R8, R9. Then the part that actually matters: every pointer from userspace is validated before you touch it. Is it in the lower half? Is the whole range mapped in this address space? Is it user-accessible? Write copy_from_user and copy_to_user and never dereference a user pointer directly, anywhere, for any reason.

Then an ELF64 loader — check e_ident, walk the program headers, and for each PT_LOAD map at p_vaddr with permissions from p_flags, copy p_filesz bytes and zero the remaining p_memsz - p_filesz for BSS. Then fork: clone the address space, clone the calling thread with identical registers except RAX = 0 in the child.

Build fork on copy-on-write from the start, since Phase 10 gave you the fault machinery. Map shared frames read-only into both address spaces and refcount them; on a write fault to a COW page, allocate a fresh frame, copy, remap writable, decrement, and when the count reaches one make the last holder writable again. Then exec, exit, wait, zombie reaping, and reparenting orphans to PID 1.

Done when a test forks a thousand times and free frame count returns exactly to baseline. A drift of one frame is a real leak — stop and find it, because it will still be there in month twelve. And every malicious pointer you can invent — null, kernel addresses, unmapped pages, ranges that start valid and cross into unmapped memory — returns -EFAULT rather than panicking.
14

Signals and the terminal layer

Both missing from the guide, and both are why its week-47 "userspace shell" wouldn't really be a shell.

Signals: a pending mask and a handler table per process, delivery checked on the return path to userspace, and a trampoline that pushes a signal frame onto the user stack so the handler returns through sigreturn. Get SIGSEGV, SIGKILL, SIGCHLD and SIGINT working.

Then a TTY layer between the keyboard and the shell: a line discipline with canonical mode (line buffering, backspace handled in-kernel), an echo setting, and control character interpretation — Ctrl-C raising SIGINT on the foreground process group, Ctrl-D signalling EOF. Process groups and a foreground group per terminal are what make job control possible later.

Done when Ctrl-C interrupts a running program and returns you to the prompt, and a program that installs a SIGINT handler survives it instead.
15

Storage: device, cache, VFS, filesystems

PCI enumeration through configuration ports 0xCF8/0xCFC, looking for vendor 0x1AF4. Then virtio-blk: feature negotiation, then the virtqueue — a descriptor table, an available ring you write, a used ring the device writes, a request as three chained descriptors (header, data, status), a kick to the notify register, and a completion interrupt. Choose virtio over AHCI: it is substantially less work for the same abstraction and it is what runs under every cloud VM in existence.

Put a buffer cache in front of it with dirty tracking and writeback before you build a filesystem, not after, or every read() hits the device and you will retrofit the cache through code that assumed synchronous I/O.

Design the VFS before the second filesystem rather than after: an inode with type, size and filesystem-private data; a dentry cache for path lookups; a file_operations vtable; a mount table; and path resolution that crosses mount points. Be explicit about refcounting and locking on inodes and dentries from day one — that is where filesystem bugs live forever. Prove the abstraction with a trivial ramfs, then implement ext2 (superblock at offset 1024, magic 0xEF53; direct then singly, doubly and triply indirect blocks are what take the time). Read support fully working first, then write.

Then add FAT32 — not because you need it, but because it is the test of whether your VFS is an abstraction or just ext2 with extra steps. If adding it requires changing VFS internals, your layering is wrong and this is the week to find out.

Done when CI builds an ext2 image on the host with mke2fs, boots the kernel, reads known files, and asserts contents byte for byte — and when a corrupted image can be diagnosed by running the host's fsck against your own writes.
16

Userspace

Write your own libc rather than porting newlib. Porting is more "correct" and teaches almost nothing; a 1,500-line libc you understand completely is worth more here than a 200,000-line one you configured. You need crt0.S, syscall wrappers, malloc/free over an mmap syscall, a stdio subset, and the string functions.

Then pipes — a ring buffer with reader and writer wait queues, correct blocking semantics (read blocks when empty unless all writers closed; write blocks when full), dup2 for redirection, and SIGPIPE now that Phase 14 gave you signals.

Then the shell as a separately compiled userspace binary: parse a line, fork, dup2 the descriptors, exec, wait. Support >, <, |, and background jobs with &. Then coreutils — ls, cat, echo, wc, ps, kill, mkdir, rm, touch, head — each a real ELF on disk. Finally a root filesystem image built by the Makefile, mounted at boot, with the kernel exec'ing /bin/init.

Done when cat file.txt | wc -l runs two processes loaded from your own filesystem, talking through a pipe you implemented, with no binaries embedded in the kernel image. That is the headline recording, and it is the moment this stops being a kernel and becomes an operating system.
17

Real hardware

Write the image to a USB stick and boot a physical machine. It will fail differently than QEMU did: real firmware memory maps have holes and reserved regions QEMU never produces, real PS/2 controllers need genuine initialisation rather than a sane assumed state, and real disks are slow enough that timing assumptions break.

Budget properly, because the debugging loop is brutal — no GDB, and only serial output if the machine has a port. This is also where your Phase 02 investment pays off the most: a kernel that can describe its own failure over a serial cable is the difference between an afternoon and a fortnight.

Done when you have a photograph of your shell running on physical silicon. It is the single best image you will ever put in that README.
18

Exactly one depth track

Not all three. Depth beats breadth, and by this point you are demonstrating judgement as much as knowledge.

SMP is the strongest signal for infrastructure and systems work: LAPIC startup, the AP trampoline that must live below 1 MB in real mode, per-CPU data through GS, IPIs, TLB shootdown, and the discovery that half your locking was subtly wrong all along because you only ever had one CPU. Networking is strongest for backend: virtio-net, ARP, IPv4, ICMP, UDP, then a minimal TCP whose state machine is a month by itself. Graphics is the weakest technically and the strongest as a demo: framebuffer, double buffering, a compositor, windows and a cursor.

Done when you have shipped one of them properly, rather than three of them halfway.

Write it down as you go

The guide leaves all the writing to weeks 53–56, by which point the details have gone. Do it at the end of each phase instead, while the bug is still fresh.

Not tutorials — nobody needs another IDT tutorial. Build each piece around a specific bug you hit and how you found it: the red zone corruption that only appeared under interrupt load, the missing slave EOI that made one IRQ fire exactly once, the COW refcount that drifted by a single frame per thousand forks. Those are the stories that demonstrate judgement rather than recall, and they are what an interviewer will actually ask you about.

One more discipline worth keeping: when a phase's "done when" check fails, fix it before starting the next phase.
